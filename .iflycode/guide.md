# iFlyCode 使用指南

本指南适用于使用 iFlyCode 进行规范驱动开发的 AI 编码助手。

## 快速检查清单

- 检索现有工作：使用列出目录文件、搜索、读文件等工具
- 确定范围：新增功能 vs 修改现有功能
- 选择唯一 `change-id`：使用 kebab-case 格式，动词开头（如 `add-`、`update-`、`remove-`、`refactor-`）
- 创建框架：`proposal.md`、`tasks.md`、`design.md`（仅需时创建）及受影响功能的增量规范
- 编写增量规范：使用`## 新增/修改/删除/重命名需求`作为标题；每项需求至少包含一个`#### 场景:`
- 验证：结束后自动执行一致性检查
- 申请审批：提案获批前不得启动实施

## 三阶段工作流

### 第一阶段：创建变更
当需要以下操作时创建提案：
- 添加功能或特性
- 实施破坏性变更（API/数据结构）
- 变更架构或模式
- 优化性能（改变行为）
- 更新安全模式

触发场景示例：
- “协助创建变更提案”
- “协助规划变更”
- “协助创建提案”
- “需要创建规范提案”
- “需要创建规范文档”

宽松匹配规则：
- 包含以下任一词：`proposal`、`change`、`spec`
- 且包含以下任一词：`create`、`plan`、`make`、`start`、`help`

无需提交提案的情况：
- 修复错误（恢复预期行为）
- 拼写错误、格式调整、注释修改
- 依赖项更新（不破坏兼容性）
- 配置变更
- 现有行为的测试

**工作流程**
1. 查看`.iflycode/project.md`或通过列出指定目录内的文件和子目录或直接读取文件理解当前上下文。
2. 选择一个以动词开头的唯一`change-id`，并在`.iflycode/changes/<id>/`目录下创建`proposal.md`、`tasks.md`、可选的`design.md`及规范变更文件。
3. 起草规范变更稿：使用`## 新增/修改/删除/重命名需求`格式，每个需求至少包含一个`#### 场景:`场景。

### 第二阶段：变更实施
将以下步骤作为待办事项逐项完成：
1. **阅读 proposal.md ** - 理解构建内容
2. **阅读 design.md **（若存在）- 复核技术决策
3. **阅读 tasks.md ** - 获取实施清单
4. **按顺序实施任务** - 依次完成
5. **确认完成** - 更新状态前确保`tasks.md`所有事项完成
6. **更新清单** - 工作完成后将所有任务标记为`- [x]`以反映实际状态
7. **审批门槛** - 提案未经审核批准前不得启动实施


### 第三阶段：归档变更
部署完成后，创建独立的拉取请求以：
- 将 `changes/[name]/` 移动至 `changes/archive/YYYY-MM-DD-[name]/`
- 若功能变更，更新 `specs/`
- 归档时识别变更 ID, 将`.iflycode/changes/<id>`目录remove到`.iflycode/changes/archive/<id>`下

## 执行任何任务前

**上下文检查清单：**
- [ ] 阅读 `specs/[功能]/spec.md` 中的相关规范
- [ ] 检查 `changes/` 中待处理变更是否存在冲突
- [ ] 阅读 `.iflycode/project.md` 了解规范
- [ ] 运行 `list_files` 查看活跃变更
- [ ] 运行 `read_file` 查看现有能力

**创建规范前：**
- 始终检查功能是否已存在
- 优先修改现有规范而非创建重复项
- 通过列出指定目录内的文件和子目录或直接读取文件查看当前状态
- 若需求模糊，请在搭建框架前提出1-2个澄清问题

目录结构

```
.iflycode/
├── project.md              # 项目规范
├── specs/                  # 当前真实状态 - 已构建内容
│   └── [能力]/       # 单一聚焦能力
│       ├── spec.md         # 需求与场景
│       └── design.md       # 技术方案
├── changes/                # 变更提案 - 待实施内容
│   ├── [变更名称]/
│   │   ├── proposal.md     # 原因、内容、影响
│   │   ├── tasks.md        # 实施清单
│   │   ├── design.md       # 技术决策（可选；参见标准）
│   │   └── specs/          # 增量变更
│   │       └── [功能]/
│   │           └── spec.md # 新增/修改/删除
│   └── archive/            # 已完成变更
```

## 变更提案创建指南

### 决策树

```
新请求？
├─ 修复缺陷以恢复规范行为？→ 直接修复
├─ 拼写/格式/注释错误？→ 直接修复
├─ 新功能/能力？→ 创建提案
├─ 破坏性变更？→ 创建提案
├─ 架构变更？→ 创建提案
└─ 不明确？→ 创建提案（更稳妥）
```

### 提案结构

1. **创建目录：** `changes/[变更ID]/`（驼峰命名法，动词开头，唯一标识）

2. **编写 proposal.md：**
```markdown
## 背景说明
[1-2句阐述问题/机遇]

## 变更内容
- [变更项列表]
- [重大变更标注**BREAKING**]

## 影响范围
- 受影响规范：[功能列表]
- 受影响代码：[关键文件/系统]
```

3. **创建规格变更文件：** `specs/[功能模块]/spec.md`
```markdown
## 新增需求
### 需求：新功能
系统必须提供...

#### 场景：成功案例
- **WHEN**用户执行操作
- **THEN**预期结果

## 修改后的需求
### 需求：现有功能
[完整修改后的需求]

## 已删除需求
### 需求：旧功能
**原因**：[删除理由]
**迁移方案**：[处理方式]
```
若涉及多个功能模块，请在 `changes/[变更ID]/specs/<功能模块>/spec.md` 下创建对应增量文件——每个功能模块单独存放。

4. **创建 tasks.md：**
```markdown
## 1. 实现步骤
- [ ] 1.1 创建数据库结构
- [ ] 1.2 实现API接口
- [ ] 1.3 添加前端组件
- [ ] 1.4 编写测试
```

5. **必要时创建 design.md：**
   若存在以下情况则创建 `design.md`，否则省略：
- 跨服务变更（涉及多个服务/模块）或新架构模式
- 新增外部依赖或重大数据模型变更
- 涉及安全性、性能或迁移复杂度
- 需在编码前通过技术决策消除的模糊性

`design.md` 最小模板：
```markdown
## 上下文
[背景、约束条件、利益相关方]

## 目标/非目标
- 目标：[...]
- 非目标：[...]

## 决策
- 决策：[内容及原因]
- 考虑的替代方案： [方案 + 依据]

## 风险/权衡
- [风险] → 缓解措施

## 迁移计划
[步骤、回滚机制]

## 待解决问题
- [...]
```

## 规范文件格式

### 关键：场景格式规范

**正确示例**（使用 #### 标题）：
```markdown
#### 场景：用户登录成功
- **WHEN** 提供有效凭证
- **THEN** 返回 JWT 令牌
```

**错误示例**（禁止使用项目符号或加粗）：
```markdown
- **场景：用户登录**  ❌
  **场景**：用户登录     ❌
### 场景：用户登录      ❌
```

每个需求必须至少包含一个场景。

### 需求表述规范
- 规范性要求使用SHALL/MUST（除非刻意非规范性，否则避免使用should/may）

### 增删改操作

- `## 新增需求` - 新增功能
- `## 修改需求` - 行为变更
- `## 删除需求` - 删除功能
- `## 重命名需求` - 名称变更

标题匹配规则：`trim(标题)` - 忽略空格

#### 新增与修改的适用场景
- 新增：引入可独立作为需求的新功能或子功能。当变更具有正交性（如新增“斜杠命令配置”）而非改变现有要求语义时，优先使用新增。
- 修改：变更现有要求的操作行为、作用域或验收标准。请始终粘贴完整更新后的要求内容（标题+所有场景）。归档工具将用您提供的内容替换整个要求；部分增量更新将丢失先前细节。
- 重命名：仅名称变更时使用。若同时变更行为，请使用“更名（新名称）+ 修改（内容）”并标注新名称。

常见误区：使用“修改”添加新内容却未包含原有文本，导致归档时细节丢失。若未明确变更现有需求，请改用“新增”创建新需求。

正确编写修改后的需求：
1) 在 `.iflycode/specs/<capability>/spec.md` 中定位现有需求。
2) 复制整个需求块（从 `### 需求：...` 到其场景部分）。
3) 将其粘贴至`## 修改后的需求`下方，并编辑以反映新行为。
4) 确保标题文本完全匹配（忽略空格），且保留至少一个`#### 场景：`。

重命名示例：
```markdown
## 重命名的需求
- 源自：`### 需求：登录`
- 目标：`### 需求：用户认证`
```

## 故障排除

### 常见错误

**“变更必须包含至少一个增量”**
- 检查 `changes/[名称]/specs/` 目录下是否存在 .md 文件
- 确认文件是否带有操作前缀（## 新增需求）

**“需求必须至少包含一个场景”**
- 检查场景是否采用 `#### 场景:` 格式（4个井号）
- 场景标题请勿使用项目符号或加粗

**场景解析静默失败**
- 需严格遵循格式：`#### 场景: 名称`

## 最佳实践

### 简约优先
- 新增代码默认控制在<100行
- 采用单文件实现直至证实不足
- 避免无明确依据使用框架
- 选择稳妥可靠的成熟模式

### 复杂性触发条件
仅在满足以下条件时增加复杂度：
- 性能数据表明现有方案过慢
- 存在具体规模要求（>1000用户，>100MB数据）
- 多个需抽象化的验证用例

### 明确引用规范
- 代码位置采用 `file.ts:42` 格式
- 规范引用格式 `specs/auth/spec.md`
- 关联变更与PR的链接

### 功能命名规范
- 动词+名词组合：`user-auth`, `payment-capture`
- 每个能力仅实现单一功能
- 遵循10分钟可理解性原则
- 若描述需用“AND”则拆分能力

### 变更ID命名规范
- 采用kebab-case格式，简洁且描述性强：`add-two-factor-auth`
- 优先使用动词前缀：`add-`, `update-`, `remove-`, `refactor-`
- 确保唯一性；若已被占用，则追加 `-2`、`-3` 等后缀

## 错误恢复

### 变更冲突
1. 运行 `list_files` 查看活跃变更
2. 检查是否有重叠的规范
3. 与变更负责人协调
4. 考虑合并提案

### 验证失败
1. 验证规范文件格式
2. 确保场景格式正确

### 缺少上下文
1. 首先阅读 project.md
2. 检查相关规范
3. 查看最近的归档
4. 请求澄清

## 快速参考

### 阶段指示器
- `changes/` - 已提议，尚未构建
- `specs/` - 已构建并部署
- `archive/` - 已完成的变更

### 文件用途
- `proposal.md` - 原因和内容
- `tasks.md` - 实施步骤
- `design.md` - 技术决策
- `spec.md` - 需求和行为

记住：规范是真理。变更是提案。保持它们同步。
