# 约束规范

本指令 **仅执行 SPEC 的「计划」阶段**。

- 优先采用简单、最小化的实现方案，仅在明确要求或确实需要时才增加复杂性
- 保持变更范围严格围绕需求目标
- 如需更多workflow规范或说明，请参考`.iflycode/guide.md` 文件（位于`.iflycode/`目录内）， `.iflycode/guide.md` 仅用于： 术语解释、文档结构规范、校验与命名规则等，不得引入新的流程步骤。

在开始正式规划前执行最后一步检查：
- 若需求存在任何模糊点（行为范围、影响范围、验收标准等），必须再次澄清后才能继续。

**必须 100% 严格遵循 `.iflycode/guide.md` 中定义的规格文档结构**。

# 规划步骤

1. 审阅`.iflycode/project.md`，并检查相关代码或文档（例如通过读文件工具），确保提案基于当前行为； 记录需澄清的任何缺失点。
2. 选择独特的动词主导型`change-id`，并在`.iflycode/changes/<id>/`目录下生成`proposal.md`、`tasks.md`及`design.md`（如需）。
3. 将变更映射为具体功能或需求，将多范围工作拆解为具有明确关联性与顺序的独立规格增量。
4. 当解决方案涉及多系统、引入新模式或需在确认规格前进行权衡讨论时，在`design.md`中记录架构论证。
5. 在`changes/<id>/specs/<capability>/spec.md`（每项能力单独文件夹）中起草规格变更，使用`## 新增/修改/删除需求`格式，每项需求至少包含一个`#### 场景:`场景描述，并交叉引用相关能力。
6. 起草`tasks.md`文件，以有序列表形式列出可验证的小型工作项，确保能呈现用户可见的进展，包含验证机制（测试、工具），并突出依赖关系或可并行化工作。

# 后置检查：design.md 中的“待解决问题”

若 `design.md` 中包含 “## 待解决问题”：

1. 在回复中逐条列出这些问题。
2. 提示用户逐条回复解决方案或确认状态。

示例提示：
以下是 design.md 中的待解决问题，请逐条回复处理方案：

问题 1：xxxx
问题 2：xxxx

**请严格按以上逻辑执行。**

# 参考工具

- 检查自动建立的文件内容是否与需求一直，并且完全覆盖用户需求
- 编写新需求前，在`.iflycode/specs`文件夹检索现有需求。
- 通过列出指定目录内的文件和子目录或直接读取文件探索代码库，确保提案与当前实现情况保持一致。
