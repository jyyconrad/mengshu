# 约束规范

- 优先采用简单、最小化的实现方案，仅在明确要求或确实需要时才增加复杂性
- 保持变更范围严格围绕需求目标
- 如需更多workflow规范或说明，请参考`.iflycode/guide.md` 文件（位于`.iflycode/`目录内）
- 禁止直接生成测试类和测试用例，只有用户明确要求时才能生成


# 实现步骤

以下步骤应按顺序执行，逐项完成：

## 1. 阅读规划文件，锁定变更范围
- 阅读并分析：
  - `changes/<id>/proposal.md`
  - `changes/<id>/design.md`（如果存在）
  - `changes/<id>/tasks.md`
- 重点识别：
  - 明确的行为变化点
  - 输入/输出影响点
  - 需求的验收标准
  - 依赖关系与任务顺序

如发现任务模糊、不明确、存在歧义（例如“优化逻辑”,“增强稳定性”），
**必须立即暂停实现，并要求用户补充具体说明**。


## 2. 根据 tasks.md 的顺序逐条执行任务
- 逐条执行 `tasks.md` 文件中的任务项
- 每个任务必须遵循：
  - 不得修改任务之外的内容
  - 不得推断或扩展需求
  - 所有编辑必须可追溯到某个明确任务

若任务之间存在依赖关系，需按文件顺序执行或按文件中注明的依赖执行。


## 3. 每完成一项任务后立即验证
- 验证代码是否符合 `proposal/design` 的要求
- 验证变更是否满足任务的验收点
- 若无法完全确定修改是否符合预期，必须主动向用户提出澄清问题


## 4. 全部任务完成后更新 tasks.md 状态
- 将每个已完成的任务更新为：`- [x] <任务内容>`
- 不得勾选未完成的任务
- 若某任务无法执行（缺少信息、需求变更等），需要主动向用户说明原因并停止流程

## 5. 最终一致性检查
全部任务完成后，需进行以下检查：

- 实际变更是否精确匹配 `proposal.md` 内容
- 是否违反最小化实现原则
- 是否遗漏 `tasks.md` 中的任务
- 是否引入未规划的行为变化

## 6. 最终一致性检查结果判断（终止步骤）
本步骤为终止型步骤，在用户明确选择前不得执行任何后续动作。

⚠ 致性检查结论（二选一）：
- 发现不一致（已修正并重新检查）
- 全部一致，等待用户选择

⚠ 说明规则：
- 若发现不一致，说明问题点与修正内容，并重新执行一致性检查
- 若全部一致，你必须首先且仅能输出以下内容，不得继续执行

⚠ 必须使用向用户提问工具提示下面内容：
一致性检查已通过，是否执行自动归档流程？
- 1 是：执行自动归档流程
- 2 否：结束本次实现

----------
⚠ 在用户明确回复前，禁止执行归档或生成任何新文件。
⚠ 若选择 `是：执行自动归档流程`，则开始执行`.iflycode/workflows/spec-4-归档.md`里面的步骤
